# AI 辅助开发总结

**任务与分工。** 我希望让研究者在聊天里提交单条蛋白质序列，随后能追溯谁选择了模型、哪一次任务生成了手里的文件。开发中使用 OpenAI Codex 阅读接口、草拟适配器、编写测试和定位错误。应用运行时使用 DeepSeek 提出工具调用。模型是否选对、任务是否执行、坐标是否属于该任务，分别用工具回执、后端记录和文件核验。

**怎样组织开发。** 先验证 React 与 FastAPI 能交换消息，再接通 DeepSeek，用只能在调用后生成的随机回执验证工具往返。随后用公开的 1UBQ 坐标打通两个 Mock 路线，检查结果展示、下载和失败状态。最后接入官方接口与 CLI。只有从聊天触发并留下完整记录的那次 Protenix 运行，才作为端到端真实推理证据。

**两条代表性指令**（按开发要求转述，非逐字聊天记录）

- 先用只包含序列的请求验证追问。读取服务端会话；刷新后只回复模型名，检查真正的工具调用是否使用刚才的完整序列。
- 在隔离任务中让执行器报错，再让它写出没有蛋白坐标的文件。核对错误码，并从浏览器确认失败卡没有可下载的结果。

**我能复述的一次调试。** 首次真实测试时，DeepSeek 在用户只给序列时猜了一个模型。页面正确地问“请选择模型”，HTTP 也是 200，但冒烟脚本没有读到预期的 76 aa 提示。沿工具回执查 SQLite，发现拒绝猜测的分支没有保存待选序列。修复有两个动作：保留与用户原文核对过的序列，并清除用户没有选择的模型。针对“刷新后只回 ESMFold2”的情况，再要求 DeepSeek 按供应商协议提供真正的工具调用，服务端照常复核参数。回归测试覆盖了模型猜测与会话恢复。本轮五轮浏览器彩排又触发了首轮选模防护，随后两个任务确实使用了同一条完整序列。[第二轮记录](verification-round-2.md) · [回归测试](../backend/tests/test_chat.py) · [本轮回执](../examples/outputs/final-rehearsal.json)

**结果与反思。** Protenix Mini 已在免费 T4 由聊天任务触发，对 76 aa 泛素生成 602 个原子；原始 mmCIF、PDB、预览和下载可交叉核对。ESMFold2 官方请求收到 HTTP 451，因此答辩采用导师允许的 Mock。本轮 131 项后端测试、前端类型检查和生产构建通过。我学到的是，验收应检查状态是否保存、模型是否真的执行以及用户实际下载的文件，而不能只看一句成功提示。下一步是在官方访问条件允许时，用同一输入补验 ESMFold2 成功返回；若要评价模型准确性，则另行设计参考结构和指标。[第六轮证据](verification-round-6.md) · [最终验收](verification-final.md)
