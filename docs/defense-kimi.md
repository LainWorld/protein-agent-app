### 1 · 从一句请求到一份蛋白质结构｜0:00–0:45

**屏幕文案**  
对话式单链蛋白质结构预测  
以 76 aa 泛素为例，跟踪从用户原文到三维坐标的全过程。

**讲解**  
给研究者一条序列，让他在聊天里选模型，然后拿到一份能够说明来历的结构文件。举例来说，用户先发泛素，模型还没选，此时连任务都不应该创建。我的目标是让每一步都能回答两个问题：刚才执行了什么？最后这份文件属于哪次请求？最终会用两个新建 Mock 任务和一份已有的真实结构演示这个区别。

### 2 · 一条消息如何变成后台任务｜0:45–1:45

**屏幕文案**  
React 聊天页 → FastAPI ⇄ DeepSeek 工具调用  
FastAPI 核验参数 → SQLite 提交会话和任务 → 单个 worker → 模型适配器  
结构通过校验 → 任务卡、Mol*、PDB 下载

**讲解**  
上半段负责理解。前端发聊天消息，FastAPI 把历史与工具声明交给 DeepSeek，拿到工具名和参数后独立校验。下半段负责执行。任务和聊天回执一起写入数据库，提交后才唤醒一个后台 worker。这样用户能先拿到编号，继续聊天。只有坐标可解析且属于该任务，后端才允许查看和下载。若服务在运行中重启，未完成的任务记为失败，避免悄悄算第二次。

### 3 · 用户如何知道结果好了｜1:45–2:45

**屏幕文案**  
聊天先返回任务编号。任务卡约每 2 秒读取后端状态。  
完成后可以旋转、缩放并下载；刷新可恢复会话。  
图注：第六轮历史聊天回执，Protenix Real 此时已排队。

**讲解**  
请看原始回执上的“已排队”和任务号。这一刻有合法任务，但还没有可以交付的文件。React 通过 GET 查询这张卡；状态进入终态就停止轮询。每次轮询都不消耗 LLM 请求。页面记住会话号，刷新后从 SQLite 恢复消息和任务。完成后，预览与下载都请求这张卡对应的结构，按钮旁仍然保留 Real 或 Mock 标记。

### 4 · 运行时 Agent 怎样选择工具｜2:45–4:00

**屏幕文案**  
`predict_structure(sequence, model)`：核对原文或本会话已确认的序列。  
`get_job_status(job_id)`：只查本会话，返回数据库状态。  
工具结果按原调用 ID 发回 DeepSeek；相同请求可复用回执。

**讲解**  
Codex 是开发助手；用户点发送时真正工作的模型是 DeepSeek。本次彩排只发序列，它就尝试了预测工具。因为用户没有选模型，工具只返回 ask_model，任务数仍为零。用户补回 ESMFold2 后，它必须真正发出含完整参数的工具调用。再用英语要求相同序列改用 Protenix，后端只在同会话中取回已确认的序列。明确指定任务号查询时，读数据库得到真实状态。每轮最多三次模型响应、四个工具调用，相同调用不重复执行，模型生成的自由文本不能决定任务是否完成。

### 5 · ESMFold2 和 Protenix 各验证到了哪一步｜4:00–5:10

**屏幕文案**  
ESMFold2：第四轮真实请求被 Biohub 以 HTTP 451 拒绝；现场用明确标记的 1UBQ Mock。  
Protenix：第六轮从聊天触发官方 Mini CLI；免费 T4，1 条链，76 aa，602 个原子。  
`protenix_mini_default_v0.5.0`，seed 101，关闭 MSA 和模板。

**讲解**  
两个模型分别配置 Real 或 Mock。ESMFold2 接的是官方 fold 接口，第四轮请求保留了 451 失败记录，因而没有真实预测坐标可展示。导师允许先用 Mock 完成流程。Protenix 有两份历史证据：第五轮证明独立 CLI 能运行，第六轮由聊天建单、worker 调用同机官方 CLI 并生成结果。答辩新建的两个任务使用固定实验坐标，能够检验路由和前端。真实计算的证据要看第六轮原始归档。

### 6 · 如何证明下载的就是所展示的结构｜5:10–6:10

**屏幕文案**  
第六轮历史 Real 任务 `94e78e41…`  
原始 mmCIF → 导出 PDB → 预览与下载。两份 PDB 字节一致。  
图注：第六轮 Colab 原任务的 Mol* 画面，Mac 可只读回放。

**讲解**  
指一下图左上的任务编号，再看下载名中的编号。Protenix 保存了原始 mmCIF，应用逐原子核对导出 PDB 的身份和坐标。浏览器实际下载的文件与预览字节一致，SHA-256 以 d879db64 开头。本轮在 Mac 打开该归档，再次拖动、缩放并下载了同一任务。稍后的现场演示先走两条新 Mock，再切换到这个原任务。打开归档只读取已有结果。

### 7 · 页面已经追问，为什么下一轮仍然失败｜6:10–7:15

**屏幕文案**  
症状：收到选模追问，下一轮却接不上刚才的序列。  
定位：HTTP 200，SQLite 待选序列为空。  
修复：保存经核验的序列，清除模型猜测。用刷新、补模型、英文换模复验。  
131 项 pytest、TypeScript 类型检查、Vite 生产构建通过。

**讲解**  
第一次真实泛素测试里，后端拒绝了模型猜测，页面看起来完全正常。冒烟脚本却没读到预期的序列长度。Codex 协助我沿工具回执查到 SQLite，确认拒绝分支漏存了输入。修复时保留用户给过的序列，只丢掉模型猜出来的选择。随后用一个可控上游反复触发该分支，再用真实 DeepSeek 走完整条链。本次 Chrome 彩排首轮又触发了该防护，之后确实产生了两个不同编号、输入相同的任务。

### 8 · 结果边界与下一步｜7:15–8:00

**屏幕文案**  
已验证真实工具调用、会话恢复、两条模型路由和 Protenix GPU 输出。  
ESMFold2 的成功返回仍待官方访问条件允许后验证。  
单个泛素案例支持工作流验证，预测精度需要另行评估。

**讲解**  
这次最重要的收获是把“页面说成功”拆成能查的几件事：工具有没有真的调用、输入有没有被改写、输出是否属于这项任务、浏览器实际拿到了什么。下一步若官方访问恢复，可以拿相同输入补验 ESMFold2 的真实成功路径。若研究问题变成模型准确性，还需要预先选好参考结构和评价指标。现在可以转入技术讨论和现场演示。
